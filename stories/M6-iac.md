# M6 — Infrastructure as Code

> Chapitres 08, 11, 12 & 13 du manuel · PVX-041 → PVX-048
> **Preuve de fin de lot** : chaîne complète `Terraform → pvecli iac inventory → Ansible → page Nginx servie`, et `pvecli iac drift` détecte une modification faite à la main dans l'interface web.

C'est le lot qui donne sa raison d'être à `pvecli` : il ne remplace pas Terraform, il **observe** l'écart entre le déclaré et le réel, et il **alimente** Ansible en données que seule l'API PVE connaît.

Prérequis : M3 (cycle de vie) et M5 (sauvegarde, pour pouvoir expérimenter sans risque). Le dépôt `proxmox-practice-lab` doit être cloné localement, chemins renseignés dans `iac.terraform_dir` et `iac.ansible_dir`.

### PVX-041 — Généraliser la garde de propriété `managed`
**Taille** M · **Type** ⚙ · **Dépend de** PVX-031 · **PRD** §5.4

En tant qu'opérateur, je veux que **toute** écriture soit bloquée sur une ressource possédée par Terraform, afin d'éliminer la double source de vérité.

**Critères d'acceptation**
- La garde introduite pour `vm rm` (PVX-031) s'applique à **toutes** les commandes W et W‼ : `set`, `clone`, `snapshot rollback`, `rm`, `template`, `migrate`.
- Détection par tag `managed` (convention du repo : `tags = ["lab","terraform","managed"]`), configurable via `iac.managed_tag`.
- Les commandes de **lecture** et les changements d'**état d'exécution** (`start`/`stop`/`shutdown`) restent autorisés : ils ne modifient pas la configuration déclarée. Ce choix est documenté et justifié dans l'aide.
- `--force-unmanaged` contourne la garde, avec un avertissement rappelant qu'il faudra un `terraform refresh`.
- Un test de service vérifie qu'aucune commande W n'échappe à la garde (parcours de la table des commandes).

**Preuve**
```bash
pvecli vm set 210 --cores 4      # → refus: possédée par Terraform, modifier main.tf
pvecli vm start 210              # → autorisé, l'état d'exécution n'est pas déclaré
```

**Ce que ça doit t'apprendre** — La frontière exacte entre ce que l'IaC déclare (configuration) et ce qu'elle ne déclare pas (état d'exécution). C'est le contrat de propriété du chapitre 13.

### PVX-042 — Générer un inventaire Ansible depuis l'API
**Taille** L · **Type** R · **Dépend de** PVX-029, PVX-011 · **PRD** §5.4, §6.2

En tant qu'opérateur, je veux `pvecli iac inventory`, afin qu'Ansible cible des IP réelles au lieu d'un fichier édité à la main.

**Critères d'acceptation**
- Produit un inventaire YAML compatible avec `docs/infra/ansible/inventory.example.yml` : groupes → hôtes → `ansible_host`, `ansible_user`.
- Les hôtes proviennent de `GET /cluster/resources` ; l'IP provient de l'agent QEMU (PVX-029), **jamais** d'une supposition.
- Groupement par tag PVE : `--group-by tag` place une VM taguée `lab_apps` dans le groupe `lab_apps`.
- `--tag <t>` filtre ; `--user ops` définit `ansible_user` (défaut lu depuis `ciuser` de la config cloud-init si présent).
- Les guests **arrêtés** ou **sans agent répondant** sont exclus et **listés sur stderr** — jamais silencieusement omis.
- `-o file` écrit le fichier ; l'en-tête généré contient `# GENERATED BY pvecli — DO NOT EDIT` et l'horodatage.
- `--format json` produit un inventaire dynamique consommable par `ansible-inventory -i`.

**Preuve**
```bash
pvecli iac inventory --group-by tag --user ops -o /tmp/inventory.yml
ansible-inventory -i /tmp/inventory.yml --list | jq '.lab_apps.hosts'
```

**Ce que ça doit t'apprendre** — Pourquoi l'inventaire est le point de jonction fragile entre provisionnement et configuration, et pourquoi il doit être **dérivé**, jamais maintenu à la main.

### PVX-043 — Lire l'état Terraform
**Taille** M · **Type** ⚙ · **Dépend de** PVX-041 · **PRD** §13 (D2)

En tant que développeur, je veux extraire les ressources Proxmox du state Terraform, afin de pouvoir les comparer au réel.

**Critères d'acceptation**
- Lecture via `terraform show -json` exécuté dans `iac.terraform_dir` (décision **D2** tranchée en faveur de la commande plutôt que du fichier brut — le format du state est interne à Terraform).
- Extrait les ressources de type `proxmox_virtual_environment_vm` / `_container` : `vm_id`, `name`, `node_name`, `cpu.cores`, `memory.dedicated`, `tags`, `disk`, `network_device`.
- Si `terraform` est absent du PATH, message explicite avec la commande d'installation ; si le state est vide, message distinguant « pas encore appliqué » de « erreur de lecture ».
- **Le state n'est jamais écrit ni modifié** par `pvecli` — lecture seule, garantie par un test.
- Aucune valeur marquée `sensitive` n'est affichée.
- Le choix retenu pour D2 est consigné dans `docs/LEARNING-LOG.md`.

**Preuve**
```bash
pvecli iac state -o json | jq '.[] | {vm_id, name, node_name}'
```

**Ce que ça doit t'apprendre** — Que le state Terraform est une base de données, pas un fichier de config : on l'interroge via l'outil, on ne le parse pas à la main.

### PVX-044 — Détecter la dérive
**Taille** L · **Type** R · **Dépend de** PVX-043 · **PRD** §3.2, §5.4

En tant qu'opérateur, je veux `pvecli iac drift`, afin de voir immédiatement ce qui a été modifié en dehors de Terraform.

**Critères d'acceptation**
- Compare, pour chaque ressource du state : `cores`, `memory`, `tags`, `name`, `on_boot`, disques, interfaces réseau — état live (API) vs état déclaré (state).
- Trois catégories distinctes en sortie : **modifié** (présent des deux côtés, valeurs divergentes), **orphelin** (dans le state, absent du live), **non géré** (dans le live, absent du state).
- Sortie table lisible + `-o json` exploitable en CI.
- Code de sortie `0` si aucune dérive, `1` si dérive détectée — utilisable en tâche planifiée.
- Les champs dont la divergence est **normale** (IP en DHCP, uptime, statut d'exécution) sont explicitement exclus, et cette liste d'exclusions est documentée.
- `--only modified|orphan|unmanaged` filtre.

**Preuve** *(un des deux critères de fin de lot)*
```bash
pvecli vm set 210 --cores 4 --force-unmanaged   # modification hors Terraform
pvecli iac drift                                 # → 210: cores 2 (déclaré) ≠ 4 (live)
echo $?                                          # → 1
```

**Ce que ça doit t'apprendre** — Pourquoi la dérive est un problème d'**exploitation**, pas de tooling : elle survient dès que deux chemins d'écriture coexistent, et elle est invisible tant qu'on ne la mesure pas.

### PVX-045 — Adopter une ressource existante dans Terraform
**Taille** M · **Type** R · **Dépend de** PVX-044 · **PRD** §6.2

En tant qu'opérateur, je veux `pvecli iac adopt <vmid>`, afin de faire passer sous Terraform une VM créée à la main sans la recréer.

**Critères d'acceptation**
- Génère un bloc `import` Terraform (syntaxe `import { to = …, id = … }`) avec l'identifiant attendu par le provider `bpg/proxmox` (format `<node>/<vmid>`).
- Génère aussi une **ébauche de bloc `resource`** pré-remplie depuis la config live, à compléter à la main.
- Rappelle la séquence : ajouter le bloc → `terraform plan` → ajuster jusqu'à obtenir « no changes » → `terraform apply` → taguer `managed`.
- N'écrit **jamais** dans les fichiers `.tf` : la sortie est affichée ou dirigée par redirection, la décision reste humaine.
- Fonctionne pour QEMU et LXC.

**Preuve**
```bash
pvecli iac adopt 211 >> /tmp/adopt.tf
# copier dans main.tf, puis: terraform plan  → doit converger vers "no changes"
```

**Ce que ça doit t'apprendre** — Que l'import Terraform est un exercice de rétro-ingénierie : le state n'accepte la ressource que si le code décrit *exactement* ce qui existe déjà.

### PVX-046 — Encadrer `terraform plan` et `apply`
**Taille** M · **Type** W · **Dépend de** PVX-044 · **PRD** §6.2

En tant qu'opérateur, je veux `pvecli iac plan|apply`, afin d'entourer Terraform de vérifications API avant et après.

**Critères d'acceptation**
- Exécute `terraform plan` / `apply` dans `iac.terraform_dir`, en relayant sortie et code de retour **sans les réécrire**.
- **Pré-check** : `pvecli doctor` (endpoint, TLS, token, privilèges) + détection de dérive → avertit si une dérive existe avant d'appliquer.
- **Post-check** : relit les ressources créées via l'API et affiche leur état réel ; `iac drift` doit revenir vide.
- Le secret de token est passé à Terraform par l'environnement (`TF_VAR_proxmox_api_token`), **jamais** écrit dans `terraform.tfvars`.
- `apply` demande confirmation en plus de celle de Terraform, sauf `--yes`.
- La CLI ne réimplémente ni ne masque Terraform : elle l'encadre. L'aide le dit explicitement.

**Preuve**
```bash
pvecli iac plan
pvecli iac apply --dry-run     # → exécute plan, montre ce qui serait appliqué
```

**Ce que ça doit t'apprendre** — Le cycle complet du chapitre 11 : plan → apply → état → dérive → dépannage, avec la vérification côté API que Terraform ne fait pas lui-même.

### PVX-047 — Encadrer `ansible-playbook`
**Taille** M · **Type** W · **Dépend de** PVX-042 · **PRD** §6.2

En tant qu'opérateur, je veux `pvecli iac configure`, afin de jouer les playbooks du repo sur un inventaire toujours à jour.

**Critères d'acceptation**
- Génère l'inventaire (PVX-042) dans un fichier temporaire, puis exécute `ansible-playbook -i <inv> <playbook>` dans `iac.ansible_dir`.
- `--playbook site.yml|docker.yml|stack.yml` (défaut `site.yml`), `--limit`, `--check` (mappé sur le mode check d'Ansible), `--tags`.
- **Test d'idempotence intégré** : `--idempotence` rejoue le playbook et échoue si le second passage rapporte `changed > 0`.
- Pré-check : tous les hôtes de l'inventaire répondent à `ansible -m ping`, sinon liste les injoignables et s'arrête.
- Post-check : validation applicative optionnelle via `--verify-url http://{{host}}/`.

**Preuve**
```bash
pvecli iac configure --playbook site.yml --check
pvecli iac configure --playbook site.yml --idempotence   # 2e passage: changed=0
```

**Ce que ça doit t'apprendre** — L'idempotence n'est pas une propriété déclarée mais **mesurée** : un playbook n'est idempotent que si le second passage ne change rien. C'est la compétence validée par le chapitre 12.

### PVX-048 — Exécuter la chaîne complète de bout en bout
**Taille** M · **Type** ⚙ · **Dépend de** PVX-046, PVX-047 · **PRD** §12

En tant qu'apprenant, je veux enchaîner template → Terraform → inventaire → Ansible → validation, afin de prouver que la chaîne du chapitre 13 fonctionne sans intervention manuelle.

**Critères d'acceptation**
- Séquence exécutée intégralement en ligne de commande, sans ouvrir l'interface web.
- La page Nginx déployée par `site.yml` répond en HTTP 200 sur l'IP découverte via l'agent QEMU.
- `pvecli iac drift` revient vide en fin de chaîne.
- Une modification faite **volontairement dans l'interface web** est ensuite détectée par `iac drift`, puis résorbée par `terraform apply`.
- Le contrat de propriété est vérifié : `pvecli vm set` sur la VM gérée est refusé.
- Toute la séquence, ses écueils et le temps réel passé sont consignés dans `docs/LEARNING-LOG.md`.

**Preuve** *(preuve de fin de lot M6)*
```bash
pvecli vm template 9000                 # template cloud-init prêt
pvecli iac apply --yes                  # Terraform crée lab-app-01 (VMID 210, tag managed)
pvecli iac inventory --group-by tag -o /tmp/inv.yml
pvecli iac configure --playbook site.yml --idempotence
curl -sI http://$(pvecli vm ip 210)/ | head -1     # → HTTP/1.1 200 OK
pvecli iac drift                                    # → aucune dérive
pvecli vm set 210 --cores 4                         # → refusé (managed)
```

**Ce que ça doit t'apprendre** — Le contrat de propriété du chapitre 13 : chaque ressource a **un** propriétaire, et l'outillage doit rendre la violation de ce contrat difficile, pas seulement déconseillée.
